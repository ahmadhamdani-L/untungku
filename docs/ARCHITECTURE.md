# Architecture and data invariants

`lib/domain`: immutable sale/product snapshots and exact integer Rupiah arithmetic. Rates are basis points. Fees round half up once per transaction, after seller discount. Line costs are captured at sale time so changes to product cost do not rewrite history. Packaging and per-unit additional costs are separate from COGS. Expenses are subtracted once in dashboard period totals.

`lib/data`: Drift SQLite database, private application-support directory. Version 1 uses separate product, sale, sale-item relationship, expense, stock-movement, and settings tables. Immutable snapshots are JSON payloads; sale-item and movement relationships additionally use SQL foreign keys, with foreign-key enforcement enabled on every open. Future schema changes must ship tested migrations; no released upgrade path exists yet. No mutable revenue/profit totals are stored.

Inventory uses product stock plus an append-only stock ledger. Changes and ledger entries commit inside SQLite transactions. Backup validation reconciles ledger totals with stock. Negative inventory is rejected by default. The owner may explicitly enable negative stock after confirmation for backorders; negative units remain visible in stock and ledger records. The policy cannot be disabled until negative quantities have been resolved. Backup validation preserves the policy and rejects negative stock when the policy is disabled. Sale edits reverse the old stock effect before applying the new quantities in one transaction. A failure rolls back reversals and new effects. Voids are idempotent. Partial returns are represented by editing quantities; full cancellation restores quantities. Damaged/unresellable returns require an explicit negative correction with reason after cancellation.

Product archive retains history and prevents new sales. Editing a sale uses its original cost snapshot. Adjustments require reasons. Initial stock and form edits create ledger records. Hard product deletion is intentionally unavailable when historical relationships exist.

`lib/features`: Material 3 screens, Riverpod change notifications, Indonesian integer amount input and formatting, adaptive wrapping and scrollable forms. UI delegates financial arithmetic to the domain layer and persistence to Store. Dashboard local date intervals are half open and exclude voids. Weekly/monthly windows are rolling 7/30 local calendar days. Best-seller counts group by stable product ID, preserving totals through renames and keeping identically named products distinct.

Backups are versioned JSON, validated in memory before any write; size is limited to 20 MB. Restore occurs in a database transaction. UI additionally writes a recovery snapshot into application support before restore. Export JSON to an external location before uninstall; internal recovery files are lost on uninstall. CSV quotes every field, doubles quotes, includes UTF-8 BOM and CRLF row boundaries. Exported cells are data; spreadsheet users should import text fields as text rather than evaluate untrusted formulas.

Ads remain disabled/mock by default. The owner profile enables the persistent banner above navigation and preloaded completion interstitials. Eligible placements are successful new sales, new expenses, and receivable settlements, after local commit and explicit completion confirmation. Edits, validation errors, cancellations, restore, app launch and tab navigation never trigger interstitials. One shared policy requires three completed tasks, a two-minute session grace period, three-minute spacing, and a five-impression session cap. Unavailable or expired ads are skipped rather than loaded and shown later. UMP permission and foreground state are checked before display; privacy changes invalidate cached ads. Load failures use bounded backoff. Rewarded remains an adapter without a product placement.

Receivables are additive fields in the existing sale JSON payload, not new SQL columns. Legacy sales default to fully paid. Credit sales include customer, optional due date, and payment records with stable IDs. Settlement reads the latest persisted sale in a database transaction, rejects duplicate-ID conflicts and overpayments, and updates only that sale payload. Identical repeated payment IDs are idempotent. Sale revisions cannot overwrite changed payment metadata and cannot reduce the total below the amount already paid. Cancellation preserves payment history and excludes the sale from active receivables; refunds are handled separately outside the app. New backups use version 2; restore accepts versions 1 and 2, validates payment IDs, amounts and dates before writing, and retains SQLite schema version 1. CSV includes payment status, outstanding balance and payment history as JSON.

Supported baseline: Android API 24+, Java 17; pinned Flutter SDK and dependencies in CI. Release signing uses an externally supplied keystore and environment values. Release build never falls back to debug signing. APK debug and signed AAB are distinct artifacts.

Baseline schema is exported at `test/schema/drift_schema_v1.json`. Before a version 2 release, preserve this baseline, raise `schemaVersion`, supply an explicit Drift upgrade migration, and test old database fixtures with the Drift schema migration tools. Regenerate the snapshot using `dart run drift_dev schema dump lib/data/database.dart test/schema`.


## v2 modular additions

Existing files remain the baseline. Domain modules in lib/domain/business implement purchasing, stock, cashflow, POS, CSV and deterministic insights. Drift schema 2 is additive; schema-1 fixture and snapshots remain. Receipt projections never post sales. Android Bluetooth channel serializes bounded Classic SPP writes and closes sockets; no automatic print retry. Security lives in lib/core/security; PIN verifier resides only in secure storage, root gate covers all routes, AES-GCM envelope v1 wraps Store payload v3. PIN/backup derivation occurs in isolates. CSV compute callbacks are top-level to prevent capturing UI/Riverpod objects. Business data remains local. No remote publication in the v2 task.
