# Security design

Implemented 2026-11-05; acceptance specification §13. Dependencies: cryptography 2.9.0 and flutter_secure_storage 11.2.0 (pub get completed). No custom cipher.

PIN: optional 4–6 digits, unique 16-byte secure random salt, PBKDF2-HMAC-SHA256 / 600,000 iterations / 256-bit verifier. Fixed-length XOR comparison. Only the verifier, salt, timeout and failure counter are stored in Android secure storage. `resetOnError: false` prevents silently discarding inaccessible credentials. Storage/corruption errors fail closed. No plaintext PIN, reversible PIN, developer bypass or PIN data in business backups. Attempts are serialized and persistent: after five failures wait 30 seconds; after ten, 300 seconds. Change/disable requires current PIN. A generation guard prevents verification completing after a new background/idle lock from unlocking the app; PIN changes are serialized. Supported idle intervals: 30/60/300 seconds, plus immediate locking on background/inactive. Pointer, hardware key and focused text-controller edits (including soft-keyboard input) reset inactivity. The root gate covers the navigator and removes hidden routes from focus/semantics. PIN is access control, not database encryption or protection against a rooted device/OS compromise.

Recovery: setup requires acknowledgement that a forgotten PIN cannot be recovered locally. No data is erased after failed attempts. Keep an external encrypted backup and its password; restore on a new installation. Secure storage is intentionally excluded from backups and Android application backup is disabled. Do not uninstall an installation containing the only copy of business data.

Encrypted backup: business payload schema v3 is wrapped by encrypted envelope v1 (`untungku-encrypted`). AES-256-GCM; fresh 16-byte salt and 12-byte nonce; 16-byte authentication tag. PBKDF2-HMAC-SHA256 / 600,000 iterations / 256-bit key. Envelope format, cipher, KDF, iteration count and byte lengths are strictly checked; algorithm/version context is authenticated as associated data. Derived key binds the random salt; GCM authenticates nonce/ciphertext/tag. Expensive derivation occurs in a worker isolate. Export passwords are 12–256 characters and require confirmation. Password input controllers are owned and disposed by the dialog widget, after its route transition, rather than a guessed delay. No passwords are logged or persisted. Authentication precedes JSON record parsing. Wrong password/tampering gets one error without modifying current data. Bounds: 20 MB plaintext, 28 MB envelope input.

Restore: legacy unencrypted payload v1/v2 and current v3 remain accepted by Store validation. Decrypt first if encrypted, validate references/schema, show counts, confirm replacement, write an application-private recovery snapshot, then atomic Store restore. These internal recovery snapshots and explicitly selected JSON exports are unencrypted; PIN does not encrypt them. Native sharing uses plugin-managed cache files; the OS/plugin controls cache lifetime. Crypto itself writes no temporary plaintext/password files. Production secure storage errors never cause an automatic reset.

Executed evidence: test/security_test.dart covers AEAD roundtrip/randomness/wrong password/tag tamper/invalid KDF metadata and no replacement before validation, persistent PIN lockout, change and disable. UI/native/security regression results are recorded in PROGRESS.md and the validation report. Synthetic test credentials are not production secrets. No claim of independent cryptographic audit.
